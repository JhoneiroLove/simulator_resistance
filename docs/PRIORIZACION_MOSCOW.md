# Priorización de Requerimientos - Método MoSCoW

| Requerimiento | Clasificación (MoSCoW) | Justificación de la Prioridad |
|---------------|------------------------|-------------------------------|
| RF-01: Identificación de Especie Bacteriana | Must Have | Requisito fundamental para inicializar cualquier simulación. Sin la especificación del organismo objetivo (P. aeruginosa) y contexto clínico, el sistema no puede determinar qué datos científicos aplicar (breakpoints, MICs baseline, mutaciones disponibles). |
| RF-02: Generación de Perfil Bacteriano | Must Have | Núcleo funcional del simulador. La generación automática de genotipos basados en escenarios clínicos (sensible, MDR, XDR) es la propuesta de valor principal del sistema. Sin esta capacidad, no existe simulación in-silico. |
| RF-03: Selección de Panel AST | Must Have | Elemento crítico para validez científica. Los paneles AST predefinidos según estándares EUCAST/CLSI garantizan que las simulaciones sean comparables con prácticas clínicas reales. Sin paneles validados, los resultados carecen de relevancia clínica. |
| RF-04: Simulación de Crecimiento Bacteriano | Must Have | Motor computacional central. La simulación de curvas de crecimiento con modelo logístico + inhibición de Hill + ruido experimental es el algoritmo que transforma genotipos virtuales en fenotipos observables. Sin esto, el simulador no funciona. |
| RF-05: Cálculo de MIC Genotipo-Fenotipo | Must Have | Puente crítico entre genotipo y fenotipo. El mapeo gen→multiplicador→MIC es la lógica científica que relaciona mecanismos de resistencia molecular con susceptibilidad antibiótica medible. Fundamental para coherencia biológica del modelo. |
| RF-06: Determinación Virtual de MIC | Must Have | Salida primaria del sistema. La determinación de MIC desde curvas de crecimiento (identificando concentración crítica por umbral OD < 0.1) es el resultado observable que los usuarios necesitan para evaluar resistencia. Sin esto, no hay utilidad práctica. |
| RF-07: Interpretación Según Breakpoints | Must Have | Traducción clínica esencial. La categorización S/I/R según breakpoints EUCAST v15.0 y CLSI M07 convierte valores MIC numéricos en decisiones clínicas interpretables. Sin interpretación estandarizada, los resultados son incomprensibles para microbiólogos clínicos. |
| RF-08: Simulación Evolutiva | Should Have | Funcionalidad avanzada valiosa. El motor evolutivo con mutaciones adaptativas bajo presión antibiótica permite estudiar dinámicas temporales de resistencia, útil para investigación, pero no esencial para simulaciones AST puntuales básicas. |
| RF-09: Cálculo de Costos de Fitness | Should Have | Refinamiento científico importante. Los costos de fitness (CI, penalización de crecimiento) añaden realismo biológico al modelar trade-offs de resistencia, pero las simulaciones básicas pueden ejecutarse sin esta capa de detalle. |
| RF-10: Visualización de Microplaca | Should Have | Mejora significativa de usabilidad. La visualización gráfica del panel 96 pocillos con código de colores facilita interpretación rápida de patrones de resistencia, pero los datos tabulares son suficientes para funcionalidad mínima. |
| RF-11: Visualización de Curvas de Crecimiento | Should Have | Herramienta de diagnóstico útil. Los gráficos OD vs tiempo ayudan a validar la simulación y detectar anomalías, pero no son estrictamente necesarios si los valores MIC finales son correctos. Valiosos para debugging y presentaciones. |
| RF-12: Tabla de Resultados | Must Have | Interfaz de salida principal. La tabla consolidada con columnas antibiótico/MIC/interpretación/guideline es la forma estándar de presentar resultados AST. Sin tabla estructurada, la información es difícil de procesar y comparar. |
| RF-13: Exportación de Resultados | Should Have | Funcionalidad de integración importante. Exportar a CSV/Excel/PDF permite análisis posteriores y documentación, pero las simulaciones pueden ejecutarse y visualizarse sin exportación. Necesario para flujos de trabajo profesionales. |
| RF-14: Progreso de Simulación | Could Have | Mejora de experiencia de usuario. El indicador de progreso con barra/tiempo estimado mejora percepción de responsividad en simulaciones largas (>5s), pero el sistema funciona sin él. Útil para mantener al usuario informado. |
| RF-15: Validación de Entrada | Must Have | Requisito de seguridad crítico. La validación integral (sanitización SQL, rangos numéricos, rutas seguras) previene errores, crashes y vulnerabilidades. Sin validación robusta, el sistema es frágil e inseguro ante inputs malformados o maliciosos. |
| RF-16: Persistencia de Datos | Must Have | Infraestructura fundamental. La base de datos SQLite con migraciones versionadas almacena los datos científicos esenciales (breakpoints, multiplicadores, paneles). Sin persistencia, cada ejecución requeriría cargar datos manualmente desde archivos. |
| RF-17: Manejo de Errores | Must Have | Requisito de robustez esencial. ErrorHandler centralizado con logging dual y rollback automático garantiza que fallos no causen pérdida de datos ni crashes. Sistema debe ser resiliente ante condiciones inesperadas para uso real. |
| RF-18: Modo Determinista/Estocástico | Could Have | Flexibilidad útil para investigación. El modo determinista (sin ruido) facilita debugging y reproducibilidad exacta, pero el modo estocástico con ruido realista es suficiente para uso normal. Útil para validación científica. |
| RF-19: Workflow Guiado | Should Have | Usabilidad mejorada significativamente. El flujo secuencial de 5 etapas con validación reduce curva de aprendizaje y errores de usuario, pero usuarios expertos podrían trabajar con interfaz menos guiada. Importante para adopción. |
| RF-20: Carga de Datos Científicos | Must Have | Base científica del simulador. La carga automática de breakpoints EUCAST v15.0/CLSI M07, matriz gen-clase con PMIDs y MICs baseline ECOFF garantiza validez científica. Sin datos curados y versionados, el simulador produce resultados arbitrarios. |
| RNF-01: Usabilidad | Should Have | Factor crítico para adopción. Interfaz intuitiva con workflow guiado, tooltips y feedback visual reduce barreras de entrada, pero la funcionalidad core puede existir con UI más básica. Esencial para usuarios no expertos en programación. |
| RNF-02: Instalación | Must Have | Requisito de distribución crítico. Scripts automatizados (install.bat/sh) que configuren entorno, dependencias y BD sin intervención manual son indispensables para que usuarios puedan ejecutar el software. Sin instalación simple, el alcance es limitado. |
| RNF-03: Seguridad | Must Have | Requisito de calidad obligatorio. InputValidator centralizado que previene SQL injection, path traversal y XSS es esencial para software que procesa inputs de usuario y accede sistema de archivos. Vulnerabilidades son inaceptables. |
| RNF-04: Protección | Must Have | Confiabilidad operacional crítica. Manejo robusto de errores con logging, rollback y decoradores @safe_method garantiza que fallos no corrompan datos ni causen crashes. Sistema debe ser estable para uso sostenido. |
| RNF-05: Sostenibilidad | Should Have | Optimización significativa (120× speedup cache). LRU cache, vectorización NumPy y connection pooling mejoran performance drásticamente (panel 96 wells en 5.1s vs >60s sin optimización), pero simulaciones funcionan aunque sean más lentas. |
| RNF-06: Accesibilidad | Could Have | Inclusión deseable. Cumplimiento WCAG AAA con shortcuts, screen readers y alto contraste amplía audiencia a usuarios con discapacidades, pero no es bloqueante para funcionalidad core. Importante para software educativo/institucional. |
| RNF-07: Performance | Should Have | Experiencia de usuario crítica. Tiempos de respuesta aceptables (panel < 10s, MIC < 10ms) mantienen fluidez interactiva. Simulaciones lentas (>30s) causan frustración, pero el sistema funciona con performance degradada. Umbral de usabilidad. |
| RNF-08: Portabilidad | Must Have | Alcance multiplataforma esencial. Soporte Windows/macOS/Linux sin dependencias externas maximiza audiencia. Restricción a una sola plataforma limitaría adopción (instituciones usan diversas plataformas). PathLib y PyQt5 garantizan portabilidad. |
| RNF-09: Confiabilidad | Should Have | Validación científica importante. Reproducibilidad mediante semillas aleatorias configurables y modo determinista permite verificar resultados, crucial para investigación científica. No esencial para simulaciones exploratorias casuales. |
| RNF-10: Mantenibilidad | Should Have | Sostenibilidad a largo plazo. Arquitectura en capas, docstrings Google style y type hints facilitan extensión y corrección de bugs. Importante para evolución del proyecto, pero no afecta funcionalidad inmediata. |
| RNF-11: Escalabilidad | Won't Have (Now) | Extensión futura. Diseño extensible para agregar especies bacterianas (E. coli, K. pneumoniae) es deseable, pero el enfoque actual en P. aeruginosa es suficiente para MVP. Complejidad adicional no justificada sin demanda validada. |
| RNF-12: Trazabilidad | Could Have | Auditoría útil. Registro completo de parámetros, timestamps y versionado de datos permite reproducir simulaciones históricas, útil para investigación formal, pero no necesario para uso exploratorio diario. Añade overhead de almacenamiento. |
